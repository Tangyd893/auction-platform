# Auction Platform - 项目概述与技术架构

## 一、项目定位与核心责任

**Auction Platform（在线拍卖系统）** 是一个基于 Go + gRPC 的高性能在线拍卖后端学习项目，旨在展示如何在轻量级技术栈上实现完整的分布式拍卖业务逻辑。

### 核心责任

1. **拍卖业务核心**：支持发布拍品、实时竞价、拍卖结束自动成交、订单管理全流程
2. **gRPC 通信标准**：提供 Protobuf 定义的全部 4 种 RPC 模式（Unary、Client Streaming、Server Streaming、Bidirectional Streaming），**后端完整实现**
3. **工程化示范**：展示 Clean Architecture 分层、接口抽象、单体测试、容器化部署
4. **前端集成**：React 18 前端通过 **REST API（HTTP/JSON）** 与后端通信（2026-04-20 变更，详见 `docs/grpc-web-white-screen-bug.md`）

### 明确不承担的责任

- **支付网关集成**：支付模块接口已预留（`CreatePayment`，`ExecutePayment`），但**不做实际集成**；支付是金融级系统，需要资质和合规，实际项目应接入支付宝/微信/Stripe 等
- **用户认证外部依赖**：JWT 认证自包含，不依赖外部 OAuth provider
- **图片存储**：图片 URL 字段由用户上传至外部存储（如七牛、AWS S3），系统只记录 URL
- **搜索服务**：不集成 Elasticsearch，列表查询走 PostgreSQL 模糊匹配

## 二、技术特点

### 2.1 通信协议：gRPC vs REST

| 维度 | gRPC | REST (HTTP/JSON) |
|------|------|-------------------|
| 传输协议 | HTTP/2 (二进制) | HTTP/1.1 或 HTTP/2 (文本) |
| 序列化 | Protocol Buffers | JSON |
| 带宽效率 | 高（紧凑二进制） | 低（文本冗余） |
| 类型安全 | 强（.proto 生成代码） | 弱（手写接口文档） |
| Streaming | 原生支持 4 种模式 | 需要 WebSocket 模拟 |
| 浏览器支持 | 需要 gRPC-Web 代理 | 原生支持 |
| Debug 难度 | 高（二进制难以肉眼阅读） | 低（JSON 可见） |

**本项目现状**：后端 gRPC 服务保留（:50051），前端通过 REST API（:8082）与后端通信。gRPC-Web 因与 Vite 5.x 存在系统性兼容冲突而废弃，详见 `docs/grpc-web-white-screen-bug.md`。

### 2.2 架构分层

```
┌─────────────────────────────────────────────┐
│  Frontend (React 18 + Vite)                │  port 3001
└────────────────┬────────────────────────────┘
                 │ HTTP/JSON
                 ▼
┌─────────────────────────────────────────────┐
│  Go Backend HTTP (Gin)                      │  port 8082
│  ┌─────────┐ ┌─────────┐ ┌──────────────┐  │
│  │ Handler │→│ Service │→│ Repository   │  │
│  └─────────┘ └─────────┘ └──────────────┘  │
│       │            │              │        │
│   HTTP/REST     Interfaces    PostgreSQL   │
└────┬───────────────┼───────────────┬───────┘
     │               │               │
     ▼               ▼               ▼
┌──────────┐   ┌──────────┐   ┌──────────┐
│ Prometheus│   │  Redis   │   │PostgreSQL│
│  :9090    │   │  :6379   │   │  :5432   │
└──────────┘   └──────────┘   └──────────┘

（历史架构，gRPC-Web 已废弃）
浏览器 ──gRPC-Web──► Envoy :8081 ──gRPC──► Go gRPC :50051
```

**分层原则**：
- `Handler`：接收 gRPC/HTTP 请求，调用 Service 层，返回响应
- `Service`：业务逻辑，接受接口（`BidRepo`、`ItemRepo` 等）而非具体实现，**可单元测试**
- `Repository`：数据访问层，只做 SQL/Redis 操作

### 2.3 四种 RPC 模式的实际用途

| RPC 模式 | 使用场景 | 示例 |
|---------|---------|------|
| Unary | 普通请求响应 | `Login`、`GetItem`、`PlaceBid` |
| Client Streaming | 批量提交 | `PlaceBidBatch`（一次连接提交多个出价）|
| Server Streaming | 实时推送 | `StreamBids`（订阅拍品，实时接收出价）|
| Bidirectional | 双向实时交互 | `BidirectionalBid`（一个连接同时出价+接收，**已实现服务端**）|

### 2.4 实时竞价实现方案

**当前方案（轮询，降级自 gRPC）**：
```
客户端 → 定时 GET /api/bids/:itemId
```
优点：简单可靠，所有浏览器支持
缺点：有延迟，依赖轮询频率

**计划方案（WebSocket，TBD）**：
```
客户端 → WebSocket 连接 → Go Backend
         双向实时推送出价更新
```
优点：真正实时
缺点：需要后端加 WebSocket 支持

### 2.5 工程化设计

**可测试性**：
- Service 层完全依赖接口（`BidRepo`、`ItemRepo` 等），无需真实数据库
- `bid_service_test.go`：8 个单元测试，用内存 mock 实现

**安全防护（Bidirectional Streaming）**：
- 连接数上限（`maxBidiStreams = 500`）
- 每用户限流（`maxBidsPerSecond = 5`）
- 熔断器（连续 20 次失败 → 熔断 30s）
- Nonce 防重放攻击
- 流超时（10 分钟自动断开）
- JWT 拦截器

**监控指标（Prometheus）**：
- `bids_total{result}`：成功/失败/拒绝的出价总数
- `bid_latency_seconds`：出价处理延迟分布
- `bidirectional_streams_active`：当前活跃双向流数量
- `auction_active_connections`：当前活跃连接数
- `circuit_breaker_state`：熔断器状态

## 四、关键设计决策

### 4.1 为什么不用 Java Spring Boot？

| 维度 | Go + Gin | Java Spring Boot |
|------|----------|-------------------|
| 内存占用 | ~100MB | ~650MB+ |
| 启动时间 | <1s | 5-30s |
| 吞吐量 | 高 | 高 |
| 生态 | 云原生主流 | 企业主流 |
| 学习曲线 | Go 更轻量 | 更重 |

Spring Boot 的自动配置和注解驱动适合企业开发，但在 4 核 8GB VM 上资源紧张。Go + Gin 轻量得多，gRPC 支持也更原生。

### 4.2 为什么用 Envoy 而不是 nginx？

nginx 对 gRPC-Web 支持需要特殊编译模块，且配置复杂。Envoy 是 CNCF 项目，原生支持 gRPC-Web 透明代理，配置简单：

```yaml
- name: envoy.filters.network.http_connection_manager
  typed_config:
    "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
    codec_type: AUTO
    route_config:
      virtual_hosts:
      - routes:
        - match: { prefix: "/" }
          route: { cluster: grpc_backend }
    http_filters:
    - name: envoy.filters.http.grpc_web
    - name: envoy.filters.http.cors
```

### 4.3 为什么 Bidirectional Streaming 服务端已实现但前端无法直接调用？

gRPC-Web 规范本身支持 bidirectional streaming，但 `@improbable-eng/grpc-web` v0.15.0 的浏览器客户端**尚未完整实现** bidirectional streaming client。只有 Unary 和 Server Streaming 是稳定支持的。

**当前解决方案**：前端切换为 REST API，gRPC Server Streaming 降级为轮询。长期方案为引入 WebSocket。

## 五、项目结构

```
auction-platform/
├── docs/                          # 项目文档
│   └── 项目概述与技术架构.md
├── proto/                         # Protobuf 定义
│   └── auction.proto              # 所有 RPC + 消息定义
├── backend/                       # Go 后端
│   ├── cmd/server/               # 入口（gRPC + HTTP + Prometheus）
│   ├── internal/
│   │   ├── config/               # YAML 配置解析
│   │   ├── handler/               # HTTP Handler（Gin）
│   │   ├── interceptor/           # JWT 拦截器
│   │   ├── model/                 # 数据模型（struct → DB table）
│   │   ├── repository/            # 数据访问层（PostgreSQL + Redis）
│   │   └── service/               # 业务逻辑层（可测试接口）
│   └── proto/gen/auction/         # 生成的 Go gRPC 代码
├── frontend/                      # React 前端
│   └── src/
│       ├── grpc/
│       │   ├── client.ts          # gRPC-Web API 封装
│       │   └── proto/             # 生成的 JS gRPC 代码
│       └── pages/                # 各页面组件
└── docker/                        # Docker 配置
    ├── docker-compose.yml
    └── envoy.yaml
```
